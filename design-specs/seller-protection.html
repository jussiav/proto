Design initiative · decision page

Seller protection

A seller should be able to accept an offer without hesitating. Sellers who call AutoVex at this point already get help from customer service and sales advisors, but the page never says so. This initiative names that help “AutoVex-turva” and shows it on the decision page, as a front-end A/B test with two variants.

Status: for team review · copy is a draft · build brief ready November 2026

How to read this page

  • For the team: part 1 (summary, variant 1, variant 2, open questions).

Part 1 · for the team

Summary

What it is

  • A name for help that already exists. Nothing new is built behind it: “AutoVex-turva” is the help customer service and sales advisors already give sellers who call. Its phone number is in the “Tarvitsetko apua?” (need help?) banner further down the same page.
  • Variant 1 (section 2): a card under the offers, with an AutoVex-turva logo panel beside a short statement of support.
  • Variant 2 (section 3): an “AutoVex-turvattu” row in every offer card that opens a modal on what the help covers.
  • Shown only while an offer can be accepted. Gone once the seller accepts or rejects.

Variant 1 in the prototype · variant 2 · production

Why

Take the hesitation out of accepting. Customer service and sales advisors name what makes sellers unsure at this point: whether to sell directly or trade the car in, how and when the car is handed over, why the offer is what it is, whether the dealership can be trusted, and less often a remaining car loan. After accepting, the usual question is timing: when the dealership calls, when it pays, what happens next.

Copy rules

The copy never names a risk or a problem the seller might meet with the dealership. It speaks to certainty for accepting, not to what our process or the buyer makes necessary. A dealership renegotiating after acceptance does happen, but AutoVex is not a party to the deal, so nothing here promises help with it.

2 — Variant 1: AutoVex-turva card under the offers

What the seller sees

  • A card directly under the offer cards, above the auction result. The page's plain white container, with no outline: an outline is the offer cards' mark.
  • Two halves from 768px. Left, a light grey logo panel: the gold shield with the “A” of the AutoVex logo, “AutoVex-turva”, and a check with “Ilmaiseksi sinulle” (free for you), so the name does not raise “do I have to sign up or pay?”. Right, a headline and one short paragraph. Narrower, the panel sits above the text.
  • Same parts as the auction result block (48px mark, 20px headline, 16px body), different layout, so the two read as related and not as copies.

3 — Variant 2: AutoVex-turvattu row in each offer card

What the seller sees

  • A row last in each offer card's list of facts, after the dealership's deal count and distance: the shield and “AutoVex-turvattu” (AutoVex-protected), underlined because it opens something. Every offer that can be accepted carries it, so it reads as part of what the seller gets with any offer here.
  • Pressing it opens a modal: the shield and “AutoVex-turva” as the title, one sentence on what the service is, five topics we help with, “Ota yhteyttä asiantuntijaamme” (contact our experts, which scrolls to the help banner), and last, under a thin rule, “Ilmaiseksi sinulle” to close the promise.

4 — Open questions

  • The test setup. The build brief assumes one test with three arms (control, variant 1, variant 2). If the team picks one variant, it runs as control against that one; each build snippet stands alone.
  • What the help covers. Ops should confirm customer service and sales advisors can carry each of variant 2's five topics for every seller who asks, including a remaining car loan and a trade-in, and variant 1's “aina auton luovutukseen asti” (right up to handing over the car).
  • When the dealership calls. Timing is the most common question after accepting. A typical time (“usually within a day”) would answer it, but needs real data before it can be stated.
  • After accepting. Both variants disappear once the seller accepts, which is when the timing questions start. Should a version stay on the accepted page?
  • No contact link during a counter offer. While a counter offer waits for the dealership, the help banner is hidden, so variant 2's modal has no way to reach us. Show the phone number in the modal then?
  • The name. Does “-turva” read as insurance or a guarantee? Legal and Marketing should confirm the name promises no more than customer service delivers.
  • The gold shield. Gold is not in the design system. Keep it as AutoVex-turva's own mark, or draw it in brand blue?

Part 2 · build brief

Build a VWO front-end test

Everything needed to build the test is in this part. The build code is the source of truth: use it as written. The previews in part 1 and the prototype run exactly this code.

B1 — What to build

  • One VWO front-end test, three arms. Control: the page as it is. Variant 1: the variant 1 snippet. Variant 2: the variant 2 snippet. Each snippet is the variant's whole JavaScript (its CSS, markup and behaviour) and stands alone.
  • No backend, Vue or stylesheet changes in the codebase. Nothing is stored.
  • One page: the consumer seller's decision page. Finnish only, like the page.
  • Audience: every visitor of that page. The snippets act only on consumer offer cards, so a B2B seller on the same URL sees nothing.

B2 — Where it goes

  • URL: https://autovex.fi/decision/<tender request id> (route user.offers.decision; logged-in sellers). Target /decision/*.
  • The page is a single-page app. The offers mount after load (behind a “Katso tulokset” screen on the first visit) and re-render after every action. The snippets watch the DOM and keep their elements in step; never insert twice.
  • Consumer offer cards are found by their distance row, the last fact row in the card's footer (“15 km (Helsinki)”): div.rounded-b-lg div.flex.text-xs.text-left.mb-4. The B2B card has no such row.
  • When to show: an offer is open for a decision while its card shows an accept button, a <button> whose text starts “Hyväksy” (“Hyväksy korkein tarjous”, “Hyväksy alhaisempi tarjous”, “Hyväksy lopullinen tarjous”). Accepted, rejected and expired cards show none.
  • Variant 1 insertion point: as the next sibling of the offer cards' own <section> (the one holding the cards), while at least one card can be accepted. The page grid puts 48px between sections.
  • Variant 2 insertion point: directly after each acceptable card's distance row, inside the card footer.
  • Variant 2's contact link scrolls to the <section> holding the <h5> “Tarvitsetko apua?”. That banner is hidden while a counter offer waits for the dealership's reply; then the link is left out.

  function distanceRows() {
    return document.querySelectorAll('div.rounded-b-lg div.flex.text-xs.text-left.mb-4');

  // ("Hyväksy korkein tarjous", "Hyväksy alhaisempi tarjous", "Hyväksy
  // lopullinen tarjous"). Accepted, rejected and expired cards show none.
  function canAccept(row) {
    var card = row.closest('.rounded-xl');
    if (!card) return false;
    return Array.prototype.some.call(card.querySelectorAll('button'), function (b) {
      return /^\s*Hyväksy/.test(b.textContent);
    });
  }

  function injectCss() {
    if (document.getElementById(ID + '-style')) return;
    var style = document.createElement('style');
    style.id = ID + '-style';
    style.textContent = CSS;
    document.head.appendChild(style);
  }

  function sync() {
    var rows = distanceRows();
    var open = Array.prototype.some.call(rows, canAccept);
    var existing = document.getElementById(ID);
    if (!open) {
      if (existing) existing.remove();
      return;
    }
    // The offer cards' own <section>; the page's grid puts 48px between it
    // and the section inserted after it.
    var offersSection = rows[0].closest('section');
    if (!offersSection) return;
    if (existing && existing.previousElementSibling === offersSection) return;
    if (existing) existing.remove();
    injectCss();
    offersSection.insertAdjacentHTML('afterend', MARKUP);
  }

  // The page is a single-page app that mounts after load and re-renders on
  // every action, so sync whenever the DOM changes. sync is idempotent.
  function start() {
    sync();
    new MutationObserver(sync).observe(document.body, { childList: true, subtree: true });
  }
  if (document.body) start();
  else document.addEventListener('DOMContentLoaded', start);
}());
