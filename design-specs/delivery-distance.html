Delivery distance A/B test

The delivery-distance question in ad creation, tested in three arms: the current design as control, a minimal-change Variant 1, and a Variant 2 that adds steppers and states what the distance does in the auction.

Status: running as an A/B test in production — awaiting results Scope: 3 arms — control · V1 · V2 Data key unchanged: delivery_distance August 2026

The test at a glance

Three arms, one question, one stored value. Each arm is a strictly larger change than the one before it, so the results separate "removing the default helped" from "explaining the consequence helped".

Global change — outside the test, ships to everyone

The question label is raised to match the other question labels on the page: text-base font-medium → text-xl font-bold, identical to "Missä autosi sijaitsee?" and "Kesärenkaat". Today this question reads as a minor setting rather than a required question, which is wrong for every seller regardless of which arm they land in. Apply it to control and both variants so it cannot skew the comparison — the arms differ only in the input and the explanation.

Control — the current design

Shipped today in EquipmentInfo.vue: a noUiSlider bound to an editable number field, range 50–500 km in 10 km steps, prefilled with 200 km. Shown below with the global label fix already applied, since that ships to the control arm too.

Known problems this test attacks

  • Preselected 200 km. Sellers can pass the question without considering it, and the data cannot tell a chosen 200 from an ignored one.
  • The consequence is understated. One line mentions that collection-offering dealers can bid from outside the area, but not that a wider distance means more offers without collection — the part that affects the seller's price.
  • The label is quieter than its neighbours. "Missä autosi sijaitsee?" and "Kesärenkaat" are text-xl font-bold; this question is text-base font-medium, so it reads as a minor setting rather than a required question. Fixed globally, in all three arms — not part of the comparison.
  • The slider invites false precision and is hard to set accurately on a phone, while the stored value only ever matters in coarse steps.

Variant 1 — minimal change

The cheapest arm: keep the control's field, tip text and layout, and change only what is listed below. The point of this arm is to isolate the effect of removing the default.

50–500 km

Changes vs control — exhaustive

  1. Remove the slider. Delete the <Slider> above the field; keep the number field itself, its size and its km suffix.
  2. Remove the default value. delivery_distance initialises empty instead of 200, so the field starts blank.
  3. Show the range as the placeholder. The empty field reads 50–500, which is where the removed slider's implicit min/max information goes.
  4. Empty is now possible, so it must be validated. Submitting empty shows the standard required-field error Pakollinen kenttä. in the field, cleared on first input.

Unchanged: the tip text, the 50–500 range, the 10 km rounding, the field's own styling, and everything the API receives. The label size change is global and applies to control as well, so it is not a difference between arms.

Variant 2 — steppers and a stated consequence

Everything in Variant 1, plus two changes: the value can be set by tapping instead of typing, and the one-line tip is replaced by a three-line block that states what the distance does in the auction. Changes vs control — exhaustive

  1. Everything Variant 1 changes — slider removed, no default value, 50–500 placeholder, empty caught by Pakollinen kenttä.
  2. Add − and + buttons at 50 km steps. Placed either side of the field. − is disabled while the field is empty and at 50; + is disabled at 500. From empty, the first + tap sets 50 km. Typing stays available — the buttons are an addition, not a replacement.
  3. Use the existing button component, no new one and no overrides. UiButton with type="button" variant="secondary" size="lg" iconOnly icon="minus|plus" — the production minus.svg / plus.svg icons. Secondary and its disabled state come straight from the component: blue-100/200/300 with text-blue-800 when active, bg-slate-200 with !text-slate-300 when disabled. The demo above renders this exact component, not a replica.
    Two gotchas the component leaves to the caller: type="button" is required — the field sits inside the step's <form>, and without it the button defaults to submit and reloads the page; and iconOnly is required — without it the icon keeps its label-spacing offset and sits off-centre.
  4. Replace the tip text with a fuller explanation of the consequence. Same standard funnel info line — filled blue info icon, text to its right (identical markup to "Korjaukset ja viat" on the services step) — but the copy now states what the distance actually does: dealers inside the area can offer without collection, dealers outside include collection in their offer.
  5. The text is constant. It must not change with the entered value — value-dependent content invites sellers to probe numbers to see what appears.

Behavior detail (same as Variant 1 unless noted)

  • While typing, the raw value is kept. On blur it is rounded to 10 km and clamped to 50–500; a corrected value gets the neutral grey message Arvo korjattiin välille 50–500 km. — grey, not red, because the seller did nothing wrong.
  • An empty field is not an in-field error. Only the page-level submit check flags it, since the submit button sits far below the fold.
  • Stepping or typing clears any page-level error immediately.

Behavior rules (both variants)

These apply to Variant 1 and Variant 2 alike. Control keeps its current behavior untouched.

  1. No default value. Nothing prefilled — the field starts empty in both variants.
  2. The range is visible before it is hit. The empty field shows 50–500 as its placeholder, so the limits are never a surprise.
  3. Values below 50 or above 500 are auto-corrected on blur. The message is neutral grey, not red — the seller made no mistake; the value was moved into the allowed range.
  4. Input is rounded to 10 km precision on blur (e.g. 133 → 130), silently when the value was already in range. Same rounding as control.
  5. Empty is caught at submit, not in the field. The standard Pakollinen kenttä. error appears below the field and clears on first input. No error is shown while the seller is still working through the form.
  6. No continue button inside the component. The page's own submit button remains the only one.
  7. Variant 2 only: − is disabled while the field is empty and at 50; + is disabled at 500; the first + tap from empty sets 50 km.

Data contract — identical in all arms

Aspect Rule
Stored fieldOne integer only — delivery_distance on the tender request draft, exactly as today. No flags, no extra fields, no new API surface. Prototype equivalent: details.deliveryRange in the localStorage draft.
Range50–500 km, unchanged from control. While typing, the raw value is held; blur clamps and rounds.
Precision10 km steps, unchanged from control's slider step.
Empty / untouchedControl: impossible — 200 is prefilled. Variants: stored empty, which blocks submit like any other required field. This is the difference the test measures, so make sure empty values are distinguishable from 200 in the analytics.
Dealer sideUntouched. The value keeps driving which dealers see the listing by default and whether an out-of-range dealer must include collection in their offer.
DownstreamSummary card/modal renders the raw number as "N km". No consumer changes needed in any arm.
