Seller file upload

Sellers have documents, not just photos — a service book PDF, a service report, a damage inspection. Today the funnel accepts images only, so those end up photographed page by page or not sent at all. This initiative adds one documents section to the photos step, and lists whatever was uploaded wherever the seller reviews their ad.

What production accepts today

Images only, everywhere

ImageUpload.vue is the single uploader behind every photo section, and it declares:

accept="image/jpeg,image/png,image/heic,
       image/heif,image/x-adobe-dng"

Per file: 100 MB, downscaled to 2000×2000. Per ad: image_upload.min/max = 5–30. No PDF path exists — not in the uploader, not in the sections, not in the review screens.

What that costs the seller

  • The service book is the common case. It is the document buyers ask about most, and the funnel has a whole section for it — which today can only hold photographs of its pages.
  • Anything already digital gets degraded. A PDF service report or an emailed damage inspection has to be screenshotted to be attached.
  • Or it arrives out of band — by email, or verbally on the review call — which is exactly the sort of thing autopublished ads will no longer have a call to carry.

Prototype correction shipped with this initiative

The prototype's Huoltokirja section had drifted: it accepted application/pdf and hinted "Voit ladata kuvia tai PDF-tiedostoja", which production never did. Both arms now match production's accept list exactly, and the hint is production's own section_descriptions.service. The PDF capability is now the v1 arm's contribution and nothing else, so the comparison is honest.

Variant 1 — one documents section

Added as the last section of the photos step, after the optional photos. Photos and documents stay separate: the photo sections take images, this one takes documents, and neither borrows the other's UI.

Behaviour rules

  1. Filenames, no thumbnails. A filename is what identifies a document; a rendered first page costs space and says less. This holds for images uploaded here too — attach a scanned receipt and it is listed by name like any other file.
  2. The limits are stated before uploading, not discovered by failing: accepted types, size per file, and how many files — one short paragraph under the heading, not two, so the section stays a footnote next to the photo sections above it.
  3. The byte unit is translated, not formatted in code. Finnish abbreviates megatavu as Mt and kilotavu as kt — not MB/kB. It fills {size} in both description and errSize, so a formatter that hardcodes "MB" leaks English into the one line where the seller reads the limit. Both units are translation keys (files.unitMb, files.unitKb) in the table below.
  4. The filename is the link. It opens in a new tab; there is no separate open button.
  5. Long filenames truncate with an ellipsis, not wrap or overflow — on both the photos step's list and the ad-preview modal's row, and more likely to be visible on narrow screens where the row has the least width to give the name. The full name is still the underlying file; only the display is shortened.
  6. Delete sits at the right of each row, and removes without a confirmation step — nothing is lost that cannot be re-uploaded. Same button design as a photo thumbnail's own × (prod's .remove-button: a bg-gray-100 square with a bold "+" rotated 45°) — one delete affordance across the step, not two.
  7. Errors appear under the field and name the fix — wrong type, too large, too many, unreadable. A rejected file never half-appears in the list.
  8. One file at a time fails. Selecting five files where one is too large uploads the other four and reports the one.
  9. Documents never touch the photo rules. They do not count toward the 5-photo minimum and cannot complete or block the step. A seller with a service-book PDF and no photos is still a seller with no photos.

Where uploaded files appear

Listing is not a variant. Any surface that shows the seller their own ad content lists the files when there are files — there is nothing to A/B about showing someone what they attached. On the ad preview sheet, files join the Kuvat section as a category row (label, then rows), the same shape as Ulkopuoli or Sisätilat — not a section of their own.

Data contract

Aspect Rule
New collectionDocuments are their own collection on the draft, not images with a different mime type. Filename, size and content type are the fields the UI needs; the prototype stores { name, size, type, data } under files.
Accepted typesPDF, Word (.doc, .docx) and images. Validate on both mime type and extension — Windows hands over an empty or non-standard mime for Word documents often enough that mime alone rejects valid files.
LimitsOpen question for production: the prototype caps at 1 MB per file, 5 files, because it stores the bytes in localStorage (see below). A real service-book scan is bigger — the suggested production limit is 10 MB per file, 5 files, to be confirmed. Whatever is chosen, the UI must state it: the seller should never learn a limit by hitting it.
Image countFiles never enter the image_upload.min/max count, even when the file is an image. Photo requirements are unchanged.
Dealer sideOut of scope here. Whether dealers see seller documents is a separate decision — this initiative covers the seller's own surfaces only.
Prototype-only mechanicThe prototype keeps the real bytes as a data URL in localStorage, which is why its cap is small: base64 inflates by a third and the photo data URLs already live there. Quota failures are caught and surfaced as an error rather than swallowed, because a silently dropped file looks uploaded until the next reload. Links are built as blob URLs at render time, since Chrome refuses to open a data: URL as a top-level document.

How to try it

Prototype: https://jussiav.github.io/proto → Kuvat. Switch arms from the Variants row on the prototype bar, grouped under Seller file upload, or open an arm directly:

…/photos.html?seller-file-upload=control
…/photos.html?seller-file-upload=v1

Seed car on the prototype bar loads two sample documents (a PDF and a Word file), so the surfaces that list files can be seen without walking the photos step. They are real, openable files rather than stubs — a placeholder would make the links look broken. Seeded files show up wherever files are listed regardless of arm, which is deliberate: the listing is not part of the test.

Open questions

  • Production size and count limits — the prototype's 1 MB is a storage artefact, not a proposal. 10 MB / 5 files is the suggestion.
  • All the Finnish copy in the table above is a draft awaiting approval.
  • Do dealers see these documents? If yes, that is its own change with its own review — a service book visible to dealers is a different product decision from one visible to the seller.
  • Does the review call change? A seller who attached the service book has already answered what an advisor would otherwise ask, which is worth knowing for the routing work.
